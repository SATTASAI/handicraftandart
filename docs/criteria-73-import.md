# รายการและเกณฑ์ครั้งที่ 73 ปีการศึกษา 2568

เจ้าของส่ง PDF 10 ฉบับในแชตและยืนยันให้นำเข้าเฉพาะ ป.1–6 รวมเรียนรวม/การศึกษาพิเศษที่รับประถม พร้อมใช้เกณฑ์ที่แนบและเปิดรับสมัครทันที ไม่มีการเปลี่ยนปีในเอกสารเป็น 2569 หรือสร้างกำหนดการ/สถานที่ขึ้นเอง

## หลักฐานและการตรวจทาน

`data/criteria-73-2568.json` เก็บชื่อไฟล์ จำนวนหน้า SHA-256 เลขหน้าและข้อความแต่ละหัวข้อ ตารางคะแนนย่อย คะแนนเต็ม และคุณสมบัติที่อ่านจากเอกสาร ส่วน `public/rules/` เก็บ PDF ต้นฉบับ 9 ฉบับแบบไม่แก้ไข ตั้งชื่อด้วย hash เพื่อคงเอกสารอ้างอิงของเวอร์ชันเดิม ใช้หน้า PDF จริงรวมหน้าปกในการอ้างอิง

ข้อมูลแยกโครงสร้างเดิมจากประวัติ Git นำมาใช้เป็นตัวช่วยหลังตรวจ SHA-256 ว่า PDF ทั้ง 9 ฉบับตรงกับไฟล์ที่เจ้าของแนบทุกไบต์แล้วเท่านั้น ตรวจซ้ำกับข้อความ PDF/ภาพหน้าตาราง ข้อมูลที่เดิมเป็นค่าระบบสมมติ เช่น เพดาน Winds 100 คน หรือจำนวนครูเริ่มต้น 2 คน ไม่ถือเป็นเกณฑ์จากเอกสาร

แก้จุดสำคัญระหว่างตรวจ:

- นาฏศิลป์ไทยอนุรักษ์เป็นรายการเดียว เลือก “ชุดอื่น” 8–10 คน หรือ “ระบำสวัสดิรักษา” 7 คน ไม่แยกเป็นสองรายการ/สองกลุ่มรางวัล ยอดเบื้องต้น 77 จึงแก้เป็น 76
- SKETCH DESIGN เริ่มหน้า 8 และมีตารางคะแนนหน้า 10 จึงอ้างอิงหน้า 8–10
- Winds มากกว่า 16 คน = อย่างน้อย 17 คน เอกสารไม่กำหนดสูงสุด เก็บค่าสูงสุดเป็น null ไม่แต่งเพดาน 100
- วงดนตรีร่วมสมัยไม่เกิน 25, ประสานเสียง 16–40 และ Various Ensemble 3–16 รองรับตามเอกสาร ไม่ติดเพดาน 20 คนของระบบเดิม
- วงปี่พาทย์ไม้แข็งมีผู้เล่น 12 ตำแหน่ง แต่อนุโลมครู/นักดนตรีอาชีพเป่าปี่ใน จึงรับ roster นักเรียน 11–12 พร้อมหมายเหตุให้ผู้จัดตรวจผู้เป่าปี่ในตามหน้า 12
- เติมวงเล็บปิดที่ตัวแยกข้อมูลเดิมตัดออก โดยตรวจตำแหน่งจริงจาก PDF ทุกจุด ไม่มีการแก้คะแนนเต็ม
- เกณฑ์ย่อยที่นำเข้ารวม 100 คะแนนทุกกิจกรรม เก็บวิธีแข่งขัน การหักคะแนน ข้อชี้ขาด และเกณฑ์รางวัลไว้ในข้อความ/เอกสารต้นฉบับด้วย ยังไม่มีระบบส่งคะแนนหรือจัดอันดับใหม่ในงานนี้

## การใช้งาน

รายการที่นำเข้าเปิดรับสมัครตามคำสั่งเจ้าของ มีการค้นหา กรองหมวด/ประเภท/ชั้น และแบ่งหน้า 24 รายการ เปิด “เกณฑ์การตัดสินและเอกสารต้นฉบับ” เพื่อดูคะแนนและ PDF ตรงหน้าอ้างอิง กำหนดเวลาหรือสถานที่ที่ไม่ได้รับข้อมูลยังเป็น “รอประกาศ”

ฟอร์มและ API ตรวจระดับชั้น จำนวนคน และประเภทชาย/หญิงเมื่อเอกสารระบุชัดเจน มารยาทงามอย่างไทยเรียนรวมต้องเป็นชาย 1 หญิง 1 ภาพยนตร์สั้นต้องมีนักเรียน 5 คน ครูที่ปรึกษา 2 คน และลิงก์ผลงาน HTTPS จำนวนครูอื่นที่เอกสารไม่กำหนดไม่แต่งเป็นเพดานทางการ

ผู้จัดยังต้องตรวจคุณสมบัติ โรงเรียน สมาชิก/เครื่องดนตรี และเอกสารเฉพาะกรณีตามต้นฉบับ การเลือกเรียนรวมและแนบภาพบัตรอย่างเดียวไม่ยืนยันประเภทความพิการ หลักฐาน IEP/เอกสารแพทย์เพิ่มเติมให้ผู้จัดตรวจนอกระบบก่อนยืนยันตามแนวทางที่แจ้งระหว่างทำงาน ยังไม่ได้เพิ่มช่องเก็บเอกสารแพทย์ใน milestone นี้

PDF เกณฑ์ต้องล็อกอินก่อนอ่าน `run_worker_first=true` เพื่อไม่ให้ static assets ข้ามการตรวจ session ตั้ง private/no-store เอกสารบัตรประชาชนนักเรียนยังใช้ API ตรวจเจ้าของ/ผู้จัดตามเดิม

## การนำเข้าและรักษาข้อมูลเดิม

Migration `0013_primary_criteria_73.sql` เพิ่มตารางต้นฉบับ/หัวข้อ/แค็ตตาล็อก และเพิ่มคอลัมน์โดยไม่ลบหรือสร้างตารางเดิมทับ บัญชี รหัสผ่าน session marker superadmin ID รายการแข่งขัน ทีม เอกสาร และผลตรวจเดิมคงเดิม

รายการจากแค็ตตาล็อกใช้ ID และ catalog_key ที่ผูกกับ source hash นำเข้าแบบ INSERT OR IGNORE ไม่ทับรายการที่มีผู้สมัครหรือเปิดรายการที่ superadmin ปิดไปแล้ว รายการที่ผู้จัดสร้างไว้เองไม่ถูกรวมทับด้วยการเทียบชื่อ เพราะยังพิสูจน์ไม่ได้ว่าเป็นกติกาเวอร์ชันเดียวกัน

ฐานที่มี superadmin แล้วจะสร้าง 76 รายการใน migration ทันที ฐานใหม่ที่ยังไม่มีบัญชีจะเก็บ templates ก่อน แล้วเปิดเป็นรายการเมื่อผู้ใช้ที่ล็อกอินเปิดหน้ารายการแข่งขัน โดยผูกผู้สร้างกับ superadmin เดิมจาก account_bootstrap ไม่สร้างบัญชีสมมติหรือแย่งสิทธิ์บัญชีแรก

**สำหรับผู้พัฒนา:** roster_min_students/roster_max_students เป็นจำนวนจริงของรายการใหม่ ค่า null ของ roster_max หมายถึงต้นฉบับไม่ระบุสูงสุด ถ้า roster_min เป็น null ให้ใช้ min_students/max_students เดิมเป็น fallback คอลัมน์เดิมยังคง CHECK 20 เพื่อเข้ากับฐานเดิม API และ SQL บันทึกทีมต้องใช้ effective counts ดังที่ tests ครอบคลุม ไม่อ่านจำนวนจริงจาก legacy columns โดยตรง

สร้าง SQL ซ้ำจาก snapshot ที่ตรวจแล้วด้วย `node scripts/generate-criteria-import.mjs` ห้ามแก้ไฟล์ migration ที่ใช้บน production แล้ว หากเกณฑ์เปลี่ยนให้สร้าง source hash/ID และ migration เวอร์ชันใหม่ พร้อมคง PDF เวอร์ชันเก่า

การ deploy ใช้ `npm run deploy` ตาม workflow เดิม ไม่มี prebuild hook ที่แก้ remote เพิ่มเติม ระหว่างพัฒนารัน migrations เฉพาะ D1 local แยก ไม่ได้ใช้บัญชี/เอกสารนักเรียนจริงทดสอบ

## การตรวจสอบ

`npm test` ตรวจ hash ของ PDF, เกณฑ์/คะแนนและขอบเขต ป.1–6, การเก็บข้อมูลเดิมหลัง migration, การนำเข้าซ้ำ, บัญชีแรก, การบันทึกนักเรียน 51 คนด้วยการตรวจ/insert แบบ bulk ที่ไม่เพิ่มจำนวน query ตามคน, private documents, กลุ่มเกิน 20 คน/Winds ไม่กำหนดสูงสุด, film coaches/work, gender pair และ dance variant รวมถึง auth/registration regression

Chromium ทดสอบตัวกรอง/แบ่งหน้า เปิดตารางคะแนน ดาวน์โหลด PDF แล้วเทียบ hash, การห้ามอ่าน PDF เมื่อไม่ล็อกอิน, ส่งรายการประถมพร้อมภาพสังเคราะห์, Winds 17+ และฟอร์มภาพยนตร์สั้นทั้งคอม/มือถือ ใช้ฐาน local แยกจากฐาน dev ปกติ
